## 版本概述

修一个会随使用时长必然爆发的故障：本机存储写满后小程序大面积报错。
根因是把所有草稿按逐格对象全量塞在一个 storage key 里且从不回收，攒到二三十份图纸就撑爆 10MB 配额，
之后每一次 `setStorage` 都失败——**并且报错文案全是误导性的**：作品页显示「读取云端作品失败」
（其实云端读成功了，是本机写不进），AI 任务显示生成失败（其实图纸已经生成好了，只是落不了库）。

改法是三件事：把落盘压缩到原来的约 1/10、给容量加上限、写满时先自救裁剪再重试。

## 本次修改说明

1. **落盘压缩**：`models/pattern.ts` 新增 `encodePatternCells` / `decodePatternCells`，把逐格
   `{color, colorCode}` 压成「去重调色板 + 每格下标」（透明格 `-1`）。40×40 图纸从约 160KB 降到
   约 15KB。`services/work-service.ts` 里原本独立实现的云端压缩改为复用同一套，消掉两份各自演化的编码。
2. **读取兼容按形状判定**：`restoreDraftCells()` 看 `cells` 首元素是 `number` 还是对象来区分新旧格式，
   **旧数据免迁移**——读回来展开即可，下一次写入自然转成压缩格式。格式损坏（下标越界、调色板缺失）
   则整份丢弃，不降级成空网格：空数组是一份合法的空白画布，编辑器会照常打开且不给任何提示，
   用户保存后还会把空白写回去覆盖掉原本可诊断的现场。作品记录仍在，打开时走「缺少可恢复的网格数据」提示。
3. **容量上限**：单个工作区草稿落盘 50 份、下载记录 60 条，超出按创建时间丢最旧的；当前草稿必留。
4. **写满自救**：`persistWithRecovery()` 只在配额写满时自救，`shrink()` 把草稿裁到 8 份、下载记录裁到
   10 条后重写一次；仍失败才抛 `LocalStorageError`。裁剪的是**运行态**而不是只裁落盘快照——否则页面还能
   打开一份重启即消失的草稿，比直接丢掉更误导。
5. **报错文案归位**：作品页 `refreshWorks` 拆成两个 `catch`，网络/接口失败说「云端作品加载失败」，
   本机落盘失败如实说「本机存储空间不足」；loading 复位与重渲染收敛成单点出口（`finally`），
   将来再加分支也不会漏掉 loading 导致页面一直转圈。
6. **测试**：新增 `test/work-sync/local-storage-quota.test.js`（7 例），harness 用 `JSON.stringify`
   长度近似真实配额并支持动态收紧。已做**变异验证**：去掉压缩或关掉自救后用例按期转红，
   证明测试真的锁住了行为。

## 已知限制

1. **自救会以丢图纸换可用空间**：配额真的写满时，被裁掉的**纯本机**作品的图纸会丢失（作品记录仍在，
   打开时提示缺少网格数据）。已同步过的作品不受影响——会走云端重新拉取。
   这是「全部写不进」与「丢掉最旧的几份」之间的权衡。
2. **上限是估算值**：草稿 50 份 / 记录 60 条是按「正常使用攒不到」取的，没有按真实机型配额压测；
   极端情况（超大尺寸图纸）仍可能先于条数上限写满，那时靠自救兜住。
3. **首次冷启动会重写一次**：旧格式数据读进来后，下一次 `persist()` 会以压缩格式落盘，写入体积一次性下降。
