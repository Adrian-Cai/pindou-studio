## 版本概述

从 0.30.16 到 0.30.18，连续三个版本都在补虚拟支付这条链路：0.30.16 做正向支付、0.30.17 做退款
与 iOS 问询、0.30.18 修掉「推送全被 400」并补齐握手解密。三版都是**纯服务端改动**，客户端一次没动。
到这一步链路本身已经完整，但**联调没法进行下去**——这就是本版要解决的唯一问题。

0.1 元 / 5 次的新人测试套餐「每人限购一次」。联调时只要走完一次真实支付，同一个账号之后每次下单
都会被 `NEW_USER_PACKAGE_NOT_ELIGIBLE` 挡住，没法做第二次验证。而虚拟支付这条链路恰恰需要反复
验证：发货、退款、iOS 问询三条推送各要跑通，还有真机验收 T1–T20。限购把这件事卡死了。

新增 `PAYMENT_NEW_USER_GATE_ENABLED`（默认 `true`，限购照旧生效），置 `false` 可让同一账号反复下单。
**默认值必须是开启**——这个套餐只卖 0.1 元，关掉又忘了开回来，等于对外无限量卖 5 次生成。因此
风险不在「开关本身」，而在「用完忘了恢复」，这一条写进了已知限制与发布前置条件。

另一处是 `server/.env.example` 补的说明：虚拟支付的 **AppKey 分沙箱 / 现网两套**，而服务端代码
固定按 `env=0`（现网）计算 `paySig`。只把 AppKey 换成沙箱那套、不改 `env`，签名一定验不过——
表现为「签名算法有问题」，实际是环境参数没配套改。这种故障在沙箱联调时极易误判方向。

## 已知限制

1. **`PAYMENT_NEW_USER_GATE_ENABLED` 是联调专用开关，正式环境必须保持 `true`**：置 `false` 时
   0.1 元的新人套餐可被同一账号无限次购买。该套餐本身也应在正式发布前下架（SQL 012 已注明）。
2. **小程序包与 0.30.16 完全一致**：客户端自 0.30.16 起未改，本版提审不会带来新的客户端变更。
   若审核方已审过 0.30.16 的客户端代码，本轮的审核重点应全部在服务端配置上。
3. **明文模式下不做来源加密保护**：不配 `EncodingAESKey` 时只能校验 `signature`，报文明文传输。
   推荐后台选安全模式并配齐两个值（沿用 0.30.18）。
4. **推送仍不被信任**：发货与退款扣回依旧以 `query_order` 反向验真为准（fail-closed），
   0.30.18 只是让消息能进得来，没有改变这一口径。
5. **退款后不回收已生成的作品**（只扣次数，已生成的图纸仍留在用户账号里，是刻意选择）；
   部分退款按「不区分」处理。
6. **0.30.16 遗留项仍然有效**：补单轮询告警阈值需按实际单量调；运营侧需在 MP 后台把道具发布到现网，
   iOS 还需已配置小程序简称与微信客户端 8.0.68+。

## 发布前置条件

1. **部署后端**：0.30.16 起的改动全部在服务端。
2. **配环境变量**：`VIRTUAL_PAY_PUSH_TOKEN`、`VIRTUAL_PAY_ENCODING_AES_KEY`（43 字符，
   MP 后台点「随机生成」即可），必须与 MP 后台「消息推送配置」里填的**完全一致**。
3. **填现网 AppKey**：`VIRTUAL_PAY_APP_KEY` 必须是现网那套；沙箱联调需**同时**把 `env` 改为 `1`，
   只换 AppKey 会让 `paySig` 验不过。
4. **MP 后台配置回调 URL 并订阅事件**：URL 指向 `/api/payments/virtual-notify`，订阅发货 / 退款 /
   iOS 退款问询三类事件（不能只配发货）。
5. **联调开关恢复默认**：`PAYMENT_NEW_USER_GATE_ENABLED` 置回 `true`（或删除该变量，默认即 `true`）。
6. **`generateImage` 云函数需在微信云开发重新部署**（0.30.16 起的前置项）。
7. **补跑 0.30.10 的真机验收 T1–T20**：已挂了四个版本，正式提审前必须执行完。

## 验收重点

推送链路无法在开发者工具里真实触发，必须**真机小额购买**，并用 MP 后台的「模拟推送」验证握手与解密。

| 场景 | 预期 |
| --- | --- |
| MP 后台保存推送配置 | 握手通过、配置能存住（不是「URL 不可用」） |
| 未配 Token 时后台发起握手 | 503 `VIRTUAL_PAY_PUSH_NOT_CONFIGURED`，明着失败 |
| 安全模式模拟推送 | 能解密并取到事件名，按事件分发 |
| 篡改签名的推送 | 回 200 + `ErrCode=1`，日志有 `virtual_payment_push_rejected`，**不被重试 15 次** |
| 真机购买套餐 → 发货推送 | 次数到账（配合 0.30.16 的补单轮询兜底） |
| 真机退款 | 次数按未消耗额度扣回（配合 0.30.17） |
| `EncodingAESKey` 配成非 43 字符 | 启动即报错，不是运行到解密才炸 |
| 联调期间同一账号二次购买 | 开关关闭时可下单；恢复默认后被 `NEW_USER_PACKAGE_NOT_ELIGIBLE` 挡住 |
| 0.30.10 真机验收 T1–T20 | 全部执行完毕并留记录 |
