# ToAPIs 生图 Provider 迁移需求

状态：Draft

## 1. 背景与目标

当前 AI 生图链路使用腾讯混元图生图。混元产物存在不符合产品预期的水印，因此后续切换到 ToAPIs Provider；首个候选模型为 ToAPIs 的 `gpt-image-2.5-sunburst`，最终模型名仍由服务端配置控制。

本次迁移的目标是：

1. 保持小程序现有 AI 生成页面、任务接口、额度扣减和作品落库行为不变。
2. 将服务端上游生图调用改为 ToAPIs 异步任务协议：提交、查询、下载、持久化。
3. 生成结果按原始图片完整保存，不新增或保留针对混元水印的固定裁切逻辑。
4. 迁移期间能够安全收尾已经创建的混元任务，避免部署切换导致用户任务丢失。
5. API Key、上游任务详情和临时图片 URL 始终只存在服务端受控链路。

## 2. 用户故事

- 作为小程序用户，我提交 AI 生图后，可以继续在当前页面看到排队、生成中、成功或失败状态。
- 作为小程序用户，我完成生成后，看到的是完整原图，不会被服务端固定裁切底部区域。
- 作为运营人员，我可以通过服务端环境变量切换 ToAPIs 模型和中国大陆 API Base URL，不需要重新打包小程序。
- 作为运维人员，我可以区分 ToAPIs 的鉴权失败、限流、任务失败、输出失效和下载失败，不依赖供应商原始错误文案排查。
- 作为发布人员，我可以先灰度 ToAPIs，再清理混元配置和实现，不影响存量任务收尾。

## 3. 范围

### 包含

- 服务端 AI Provider 抽象补齐异步任务状态查询。
- ToAPIs Provider：提交 GPT-Image-2.5 图生图任务、查询任务、下载结果。
- 输入图从项目自己的 AI 文件公开地址提供给 ToAPIs，不向 ToAPIs 传递 data URL 或 API Key。
- ToAPIs 配置、错误归一化、轮询节流、输出地址白名单和安全校验。
- 混元存量任务兼容与切换后的清理方案。
- Provider、配置、任务状态机、错误契约和端到端模拟测试。
- 后端设计文档、API 说明、运维验收说明和发布记录。

### 不包含

- 小程序页面交互重做。
- 修改 AI 提示词的产品语义、额度价格或支付流程。
- 引入 ToAPIs Webhook 作为第一阶段上线阻塞项；Webhook 作为第二阶段降低轮询压力的增强项。
- 同时接入多个新的生图供应商或建立通用 Provider 注册中心。

## 4. 业务约束

1. 客户端不得提交 Provider、Model、API Key、ToAPIs 任务 ID 或供应商参数。
2. 任务成功前不得扣除第二次额度；Provider 失败、查询失败、输出校验失败和下载失败均不得产生额外扣费。
3. 新任务默认使用 ToAPIs；已有 `provider=hunyuan` 的任务必须在迁移排空期继续由混元 Provider 处理，不能直接按 ToAPIs 任务查询。
4. ToAPIs 参考图接口只接受可被其服务访问的图片 URL，因此服务端必须保证生产环境 `AI_FILE_PUBLIC_BASE_URL` 为 HTTPS 且可从公网访问。
5. 轮询间隔不得低于 ToAPIs 文档建议的 5 秒；遇到 `429` 或 `503` 必须优先使用 `Retry-After`，没有该响应头时才使用退避。
6. ToAPIs 输出 URL 可能过期，任务完成后服务端必须尽快下载并持久化，不能把 ToAPIs 临时 URL 返回给小程序。

## 5. EARS 验收标准

### Provider 与配置

- 当服务端配置有效的 ToAPIs API Key、Base URL、模型和输出域名时，系统应将 AI 生成能力标记为可用，并且日志中不得出现完整 API Key。
- 当 ToAPIs 配置不完整、Base URL 不是 HTTPS 或生产环境缺少输出域名白名单时，服务端应在启动配置校验阶段拒绝启动，不应等到用户提交任务才失败。
- 当模型配置为 `gpt-image-2.5-sunburst` 或 `gpt-image-2.5-flare` 时，系统应把完整模型 ID 原样发送给 ToAPIs，不得发送系列名 `gpt-image-2.5`。

### 任务流程

- 当用户创建 AI 任务时，服务端应先落库 `queued` 任务并返回项目任务 ID，不应让 HTTP 创建请求同步等待上游出图。
- 当任务首次推进时，系统应向 ToAPIs 提交 `POST /v1/images/generations`，携带固定服务端 Prompt、参考图 URL、配置模型、`size`、`resolution`、`quality` 和 `n=1`。
- 当 ToAPIs 返回任务 ID后，系统应持久化 Provider 名称、模型快照和 Provider 任务 ID，并保持项目任务为 `processing`。
- 当 ToAPIs 返回 `pending`、`queued` 或 `in_progress` 时，系统应保持 `processing`，并按照服务端轮询时间推进，不得重复提交新任务。
- 当 ToAPIs 返回 `completed` 且结果包含图片 URL 时，系统应下载图片、校验真实格式/大小/尺寸/像素数、持久化到项目文件存储，并将项目任务置为 `succeeded`。
- 当 ToAPIs 返回 `failed`、完成结果缺少 URL、图片 URL 不受信任或下载内容无效时，系统应将项目任务置为 `failed`，返回稳定的公开错误契约，并且不扣除额外额度。

### 可靠性与安全

- 当 ToAPIs 返回 `429` 或 `503` 时，系统应按 `Retry-After` 或指数退避处理，不得在单次用户请求内长时间阻塞等待。
- 当服务端重启或切换副本时，系统应能够依据数据库中保存的 Provider 和任务 ID继续推进未完成任务；不能依赖单进程 Map 才能恢复。
- 当 ToAPIs 返回的输出 URL发生跳转、使用非 HTTPS、包含凭据或不在配置白名单内时，系统应拒绝下载。
- 当任务已成功持久化项目文件时，系统应清空临时 Provider 输出引用，避免数据库长期保存第三方临时 URL。

### 迁移与发布

- 当新版本启用 ToAPIs 时，新创建任务应使用 ToAPIs；部署前已存在的混元任务应继续按其 `provider` 快照处理。
- 当迁移排空期结束且不存在未完成混元任务时，才允许删除混元生产配置、Provider 实现和相关测试。
- 当生产发布验收完成时，至少应验证一条真实 ToAPIs 图生图成功链路、一次上游失败链路、一次限流链路和一次输出安全校验链路。
